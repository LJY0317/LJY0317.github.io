Context

How the service works

We built a robot system for greenhouse patrols and plant checks, including diagnosis and harvesting flows. The robot side runs on ROS 2; a server and dashboard display tasks and their progress.

An operator chooses a plant or a task from the dashboard. In the Gazebo greenhouse, the robot navigates the mapped aisles while the interface shows its progress. This let us test the full route without a physical greenhouse.

Responsibility

What I worked on

I ran mapping experiments in Gazebo, checked navigation behavior, and debugged ROS 2 state issues across RViz and the operator interface.

I also tried moving the final goal closer to a selected plant. Gazebo runs revealed detours and collision warnings, so I reverted the change and then fixed stale robot-position data and the starting-waypoint choice. Those changes are documented in my commits.

Problem

Nodes can start successfully while timing, TF, odometry, or localization is still wrong. I compared Gazebo and RViz to narrow down the problems.

Action

  • Ran lower-load world and mapping experiments to isolate simulation and map behaviour.
  • Checked Gazebo, RViz, transforms, odometry, and localisation startup as one connected runtime path.
  • Connected navigation flows with operator state instead of treating each component as an isolated demo.

Result

The project demo shows navigation, diagnosis, and harvesting together. The mapping and debugging recordings show how I tested the route and traced integration issues.
