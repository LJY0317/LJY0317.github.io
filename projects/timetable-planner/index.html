프로젝트와 담당 업무

Project and role

시간표와 일정, 필기, 스티커를 관리하는 학생용 앱입니다. 팀원들과 Flutter로 개발했습니다. 저는 공통 화면과 반응형 UI, 시간표 사진에서 수업을 읽는 기능, 에브리타임 공유 링크 가져오기와 관련 API를 맡았습니다.

Dayori is a Flutter app for timetables, schedules, notes, and stickers, built with my team. I worked on shared and responsive screens, timetable OCR, Everytime link imports, and the related APIs.

개발 방식에 대한 의견 차이

Choosing a development approach

저는 기기마다 익숙한 화면과 동작을 살리기 위해 아이폰과 안드로이드 앱을 따로 만들고 싶었습니다. 팀원들은 Flutter로 함께 개발하는 편을 선호했습니다. 고양이 게임과 가상 피팅 등 여러 주제를 검토하는 동안 시간이 지나, 전체 8주 중 실제 앱 개발에 쓸 수 있는 기간은 4주도 남지 않았습니다.

I preferred separate iPhone and Android apps, while teammates favored Flutter. We had considered several topics, including a cat game and virtual fitting, leaving fewer than four weeks of an eight-week project for the final app.

두 앱을 따로 만들면 화면 작업과 오류 수정도 각각 해야 했습니다. 남은 시간을 고려해 Flutter로 진행하기로 했고, 저도 공통 화면과 시간표 가져오기 기능을 그 방식으로 구현했습니다.

Separate apps would also require separate screen and bug-fix work. We chose Flutter for the remaining schedule, and I implemented my screens and import features in it.

시간표 이미지 인식 수정

Reworking timetable OCR

처음에는 사진 전체에서 글자와 위치를 읽어 과목을 묶었습니다. 시간표에는 과목명 외에 요일과 시간 눈금도 있어, 서로 다른 수업의 문구가 같은 후보로 섞였습니다. 글자가 무엇인지 읽는 일과 어느 수업에 속하는지 판단하는 일을 나눠야 했습니다.

The first version grouped classes using text and positions from the entire screenshot. Subject names, day labels, and time markers could become mixed candidates. Recognizing the text was not enough to identify which class it belonged to.

색상으로 구분된 수업 칸을 먼저 찾고, 각 칸을 잘라 따로 인식하도록 바꿨습니다. 잘라낸 이미지에서 읽은 글자의 위치를 원본 좌표로 되돌려 과목명과 장소 후보를 만들었습니다. 전체 이미지의 인식 결과는 요일과 시간 눈금의 기준으로 사용했습니다.

I changed the preprocessor to find colored class blocks and run OCR on each crop. The crop coordinates are mapped back to the original image for subject and location candidates. Full-image recognition supplies day and time anchors.

칸별 인식이 가능한 경우에는 OpenCV로 보정한 전체 이미지를 다시 읽는 단계를 건너뛰었습니다. 느린 전체 인식이 섞인 후보를 다시 만드는 것을 피하려는 변경이었습니다. 수업 칸을 찾지 못한 경우의 전체 이미지 인식은 보조 방식으로 남겼습니다.

When block crops are available, the service skips the slower OpenCV full-image OCR pass so mixed candidates do not re-enter the comparison. Full-image recognition remains available when block detection cannot supply crops.

저장 전 후보 수정

Reviewing candidates before saving

인식 결과를 그대로 저장하지 않고 과목명, 장소, 요일, 시작·종료 시간을 고칠 수 있게 했습니다. 종료 시간이 시작 시간보다 빠르거나 같으면 수정 내용을 반영할 수 없고, 유효한 수정은 미리보기 목록에 바로 표시됩니다.

The review sheet lets users edit the subject, location, day, and start and end times. It does not apply an end time at or before the start time, and valid edits are reflected in the preview immediately.

이 화면은 서버에 저장하는 기능보다 먼저 만들었습니다. 인식된 후보와 사용자가 수정한 후보를 화면 안에서 관리한 뒤, 시간표 일괄 저장 API와 연결하는 순서로 작업했습니다.

I built the review interface before connecting storage. It keeps recognized and edited candidates as local drafts, separate from the later bulk-save API integration.

에브리타임 공유 링크 가져오기

Everytime shared timetable imports

공유 링크에서 시간표 식별자를 얻고 서버에서 수업 데이터를 읽어 앱의 후보 목록으로 변환했습니다. 요일 숫자는 앱의 요일 코드로, 5분 단위의 시작·종료 시간은 분 단위로 바꿨습니다. 같은 과목이 여러 요일에 있으면 각각의 수업 후보를 만들었습니다.

The backend extracts the timetable identifier and converts the returned class data to app candidates. It maps numeric days to app day codes and five-minute time units to minutes. A subject meeting on multiple days becomes multiple candidates.

서비스 테스트에는 월요일과 수요일에 있는 한 과목을 넣었습니다. 두 개의 후보가 생성되는지, 156과 174라는 시간 값이 780분과 870분으로 바뀌는지, 요일과 강의실 정보가 유지되는지를 확인했습니다.

The service test uses a subject that meets on Monday and Wednesday. It checks two candidates, conversion of 156 and 174 time units to 780 and 870 minutes, and preservation of the days and classroom details.

잘못된 공유 링크나 비공개 시간표처럼 가져오지 못하는 경우에는 공통 가져오기 오류를 반환했습니다. 정상 결과도 바로 저장하지 않고 앱에서 먼저 검토하게 했습니다.

Invalid or private links return the same import-failure error. Successful results are still returned for review before saving.

팀 코드 병합과 화면 연결

Merging the timetable UI

팀의 최신 코드에는 시간표 API를 이용한 목록, 활성 시간표, 항목 추가·수정·삭제 기능이 들어 있었습니다. 제 작업에는 공통 상단 메뉴와 펜 입력을 연결한 화면이 있었습니다. 두 변경을 합치는 과정에서 시간표 화면과 공통 화면 구조에 충돌이 났습니다.

The team branch had the API-driven timetable list, active table, and item create/edit/delete flows. My branch had shared header controls and pen-input integration. Merging them produced conflicts in the timetable and common screen structure.

시간표 데이터 처리는 최신 API 흐름을 유지했습니다. 그 위에 전역 잉크 입력과 연결되는 키를 다시 전달하고 공통 상단 메뉴, 펜 도구 버튼, 화면 폭 계산을 함께 남겼습니다. 최신 구조에서 참조하지 않는 목업 시간표 파일은 제거했습니다.

I retained the current API flow and reconnected the key used by the global ink overlay. The common action bar, pen controls, and button-width calculations were preserved, while an obsolete mock timetable file was removed.

한쪽 파일을 통째로 선택하는 식으로는 합칠 수 없었습니다. 데이터를 가져오는 부분과 화면에서 입력을 받는 부분을 나눠 보고, 각 기능이 어디에 연결돼야 하는지 확인하며 정리했습니다.

Choosing one entire version of the conflicted file would have discarded useful work. I separated the data flow from the input and layout hooks and reconciled their connection points.
